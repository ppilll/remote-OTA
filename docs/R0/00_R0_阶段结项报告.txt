1. R0 结论
R0 的核心目标是确认目标硬件、无线能力、BSP 基线、第一版 Remote OTA 传输边界，以及确认 A/B OTA 在存储与启动体系上不存在明显硬件阻塞。当前证据已满足该目标。
领域	结论	证据/说明
硬件平台	PASS	ATK-DLRK3588，Rockchip RK3588，AArch64，eMMC 启动。
BSP 一致性	PASS	Linux 5.10.209；Buildroot 2021.11；8733bu.ko 与 rtk_btusb.ko vermagic 均为 5.10.209。
Wi-Fi	PASS	RTL8733BU/USB；wlan0 已出现；解除 rfkill 后可扫描实际 AP。
Bluetooth/BLE	PASS	rtk_btusb 加载；hci0 UP RUNNING；BlueZ 可见；支持 central/peripheral 与 advertising。
存储	PASS	当前 GPT 与 vendor parameter.txt 一致；14 GiB rootfs + 大容量 userdata。
A/B 容量	PASS	rootfs.ext2 ≈1.38 GiB；SDK parameter-ab 提供 system_a/system_b 各 7 GiB。
RTC	DEFERRED	RTC 芯片/驱动存在，但纽扣电池低电压；更换电池后在 HTTPS 前关闭。
Boot control	DESIGN BASELINE	U-Boot 具备 Rockchip A/B 相关代码与 SDK A/B 开关，但当前 CONFIG_ANDROID_AB 未开启，标准 U-Boot env backend 也未配置；后续实装阶段验证。

4. 后续关键技术决策
优先验证路径：Rockchip SDK 的 RK_AB_UPDATE / parameter-ab / misc A/B 元数据链路，并将 RAUC 通过 custom bootloader backend 对接。如果 vendor A/B 不能提供稳定的 boot-attempt / mark-good / rollback 语义，再回退到“为 U-Boot 增加持久化 environment + RAUC bootloader=uboot + BOOT_ORDER/BOOT_x_LEFT”的方案。
原因：当前编译配置明确显示 CONFIG_ANDROID_AB 未开启，同时没有 CONFIG_ENV_IS_IN_MMC 等标准持久化 environment backend；因此两条路径都不能在 R0 阶段假定为“开箱即用”。
